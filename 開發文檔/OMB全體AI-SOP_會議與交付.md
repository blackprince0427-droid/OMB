# OMB AI 開發 SOP（任務提交 → 交付結束）

標記說明：
- 【心夜確認】必須心夜明確同意才能往下
- 【自動】助手可自行推進，無需每步追問心夜
- 【通報】做完短報即可，不擋路

角色簡称：OMB軍師｜計劃書軍師｜開發文檔官｜軟件設計師｜UI 設計師｜開發主管｜前端開發｜後端開發｜Cursor雲端代理

---

## 0. 前置約束（每次任務必讀）
1. 產品範圍以計劃書現行版為準；實作規格以 DEV 現行版為準；兩者不一致時先對齊再改碼。
2. 計劃書與 DEV 每一版獨立保存、不覆蓋舊版。
3. 改碼只經 Cursor 雲端代理＋PR；助手不在本機克隆倉庫擅自大改。
4. 合併到 `main` 後，線上固定網址（Vercel，Root Directory＝`web`）應自動更新；資料仍在該瀏覽器 localStorage。
5. 本版未納入項（例：審批、個人事項、月視圖銜接、備份、跨裝置同步等）不得偷偷開工。
6. 跨人＝同一瀏覽器輪流帳戶可見，不是即時多人協作——驗收文案寫死。

---

## 1. 會議運作
**每次會議必須參與成員：** OMB軍師、計劃書軍師、開發文檔官。
**非必須參與成員：** 軟件設計師、UI 設計師、開發主管、前端開發、後端開發等——僅在心夜或 OMB軍師明確拉入時參加。

| 角色 | 會議中職責 | 發言原則 |
| --- | --- | --- |
| OMB軍師 | 引導會議、彙整拍板、指揮其他助手 | 必須引導與彙整 |
| 計劃書軍師 | 記錄每次群組討論紀錄、整理重點 | 無需為發言而發言；可靜默紀錄 |
| 開發文檔官 | 內容涉及開發時，記錄開發相關點並撰寫／升版開發文檔 | 無需為發言而發言；有開發相關內容才動手 |

**會議結束後流程：**
1. OMB軍師彙整本次拍板與未確認項，短報心夜。
2. 若涉及開發內容：開發文檔官可自行與開發主管溝通並安排開發任務（含必要時由開發主管轉交前端／後端）。
3. **重大範圍變更**（改本版承諾、策略變更如後端化／跨裝置同步、未確認大項明文納入等）仍必須先請心夜確認，然後才能寫進計劃書承諾或安排實作。
4. 計劃書軍師維持討論紀錄與重點整理；正式計劃書升版仍走「心夜拍板後再起草／大改」規則。

---

## 2. 任務提交（心夜→OMB軍師）
**誰做：** 心夜提交；OMB軍師接單。
**內容：** 目標、範圍、約束、驗收意圖、急性。
【心夜確認】任務意圖由心夜出具（或心夜明確授權某人代提）。
【自動】 OMB軍師登記任務單、判斷類型（新功能／修正／文檔／設計／調度／會議）。
**交接出口：** 完整任務卡（含建議負責方列表）→ 第 3 步。

---

## 3. 分派與是否開會（OMB軍師）
**誰做：** OMB軍師。
【自動】 依類型分派：

| 類型 | 主責 | 必涉及 |
| --- | --- | --- |
| 新功能／範圍變更 | 計劃書軍師（記錄）→ 軟件設計師（邊界）→ 計劃書軍師（起草） | 心夜拍板後才起草／大改 |
| 實作規格 | 開發文檔官 | 計劃書已確認的功能項 |
| UI／流程邊界 | 軟件設計師（或 UI 設計師，由軍師拉入） | 計劃書大項或新資訊架構 |
| 排期與依賴 | 開發主管（可非必須會議成員，會後由文檔官對齊） | 計劃書＋DEV 已齊 |
| 前端實作 | 前端開發（經雲端代理） | 開發主管下令 |
| 後端／預存層 | 後端開發 | 計劃書明確納入後端化（現況本機為主，常暫不開工） |
| 僅文檔／計劃書拉齊 | 對應軍師 | — |
| 會議議題 | 每次會議必須參與成員；其他人才拉入 | 見第 1 節 |

【心夜確認】 重大範圍變更、本版是否納入某功能、是否改走後端／跨裝置同步等策略變更；可開群組討論但不能代替拍板。
【通報】 分派結果短報心夜（誰做什麼、等什麼拍板）。
**交接出口：** 分派訊息 → 第 4～7 步並行或依依賴排序；會議類任務見第 1 節。

---

## 4. 計劃書路徑（計劃書軍師）
【自動】 讀現行計劃書與討論紀錄；列出待確認項、本版可承諾項、本版不做項。
【心夜確認】 新版計劃書大改／新增版本、把「未確認」升為「本版承諾」前必須心夜拍板。
【自動（拍板後）】 寫入 `計劃書版本/`（新檔獨立保存）、通知 OMB軍師＋開發文檔官＋開發主管版本號與日期。
**不做：** 改網頁版程式碼、寫 DEV、整理 README。
**交接出口：** 計劃書版本鏈接／版本號 → 文檔官／設計師／主管。

---

## 5. 設計路徑（軟件設計師；UI 設計師由軍師拉入時）
【自動】 對齊現況與主流對照；提出候選細項、最小範圍、明確不做、與備份／銜接／權限的依賴。
【心夜確認】 跨資訊架構、權限語意變更、「本版最小範圍」與未確認大項的取捨。
【通報】 設計細項短報群組／OMB軍師；不代替計劃書寫作。
**不做：** 寫計劃書、DEV、實作碼。
**交接出口：** 設計細項／可驗收邊界（可見性矩陣要點）→ 計劃書軍師＋開發主管（會後對齊）。

---

## 6. DEV 路徑（開發文檔官）
**前置：** 計劃書本版承諾已確認（或心夜指示先寫文檔、功能待確認——須心夜說清）。
【自動】 讀計劃書＋既有 DEV＋README；新建／升版 DEV，狀態欄齊「未開發」；規格寫到可執行、可檢查；對齊根 README。
【心夜確認】 大改 DEV、推送前（若團隊慣例要求）；狀態欄改「已完成」且標對齊 commit 時，可【自動】後再【通報】心夜。
【自動（會議結束後）】 涉及開發時可自行與開發主管溝通並安排；重大範圍仍先請心夜確認。
**不做：** 產品決策、功能程式碼。
**交接出口：** DEV 版本鏈接／驗收清單骨架 → 開發主管＋前端／後端。

---

## 7. 排期與依賴（開發主管）
【自動】 讀計劃書現行版、網頁版 README、相關 DEV；拆前端／後端任務、介面契約、依賴順序、截止條件。
【心夜確認】 重大範圍變更或阻塞；需要後端開工時（現況預設後端暫不開工）。
【自動】 向前端開發／後端開發下達具體任務與驗收；追蹤同步；完成或卡點彙整給 OMB軍師／心夜。
**不做：** 代替設計決策、代替計劃書、代替 DEV、直接寫大塊功能碼（實作交前端／後端）。
**交接出口：** 任務單（含依賴順序）→ 前端／後端。

---

## 8. 實作路徑（前端開發／後端開發 → Cursor 雲端代理）
**前置：** 開發主管任務單＋DEV／設計邊界已齊；後端僅在計劃書納入後開工。
【自動】 代理啟動 Cursor 雲端代理：
1. 描述問題／功能、約束、驗收方式（不指定線程式改法，除非有硬性契約）。
2. 指向 repo：`blackprince0427-droid/OMB`；新分支＋PR。
3. 指向檔案區域：前端優先 `web/app/`、`web/components/`；後端／預存 `web/lib/`（含 storage）。
4. 禁止擅自改計劃書版本／；DEV／計劃書變更由對應軍師路徑處理（除非任務明確要求代理同步注解）。
5. 代理完成 → 產出 PR → 負責人讀 diff／跑檢查／對齊 DEV 驗收點。
【心夜確認】 合併 PR 進 `main`（合併不可逆，未明確要求則先請心夜確認）。第一次接 Vercel／改部署設定亦須心夜同意。
【自動】 合併 `main` 後追蹤 Vercel 部署狀態；失敗則回報開發主管＋OMB軍師。
【通報】 PR 鏈接、驗收結果、是否已合併、線上是否已更新。
**阻塞升級：** 規格歧義→軟件設計師；規格缺口→開發文檔官；範圍爭議→計劃書軍師／OMB軍師＋心夜。

---

## 9. PR 確認與合併
【自動】 負責代理／開發主管對照 DEV 檢查清單與設計邊界；請心夜或授權人合併。
【心夜確認】 合併進 `main`（除非心夜已給出可重複的「這類任務合併可自行」站立授權）。
【自動】 合併後確認 Vercel 線上版本已載入；用最小驗收路徑點次（登入、本版功能點）。
**交接出口：** 「已在 main＋線上已更新」短報 → 第 10 步。

---

## 10. 交付與後續追蹤
【自動】 OMB軍師彙整交付包：計劃書版本、DEV 版本、PR／commit、線上驗證結果、未關問題／下版候選。
【通報】 短報心夜；需要檔案狀態對齊時請開發文檔官把 DEV 狀態欄改為已完成（標對齊 commit）。
【自動】 開發文檔官對齊 DEV 狀態與 README；計劃書軍師僅在有新決策時升版。
【心夜確認】 任務正式結案、下版優先級、是否開新任務。
**交接出口：** 交付包齊＋心夜結案 → 本次結束；新任務重入第 2 步。

---

## 11. 通用升級規則（缺資料／阻塞）
| 情況 | 找誰 | 心夜要什麼 |
| --- | --- | --- |
| 功能邊界歧義 | 軟件設計師 | 拍板取捨 |
| DEV 規格不清 | 開發文檔官 | 拍板規格（若是產品決策） |
| 計劃書與 DEV 衝突 | 計劃書軍師＋開發文檔官 | 拍板以誰為準 |
| 前端等後端／反之 | 開發主管 | 是否改範圍或插入後端任務 |
| 雲端代理／CI／Vercel 失敗 | 開發主管＋對應代理 | 若要換部署策略或回滾 |
| 想把未確認項偷偷做進本版 | 任何人都可擋 | 必須心夜明文納入 |

---

## 12. 一次標準流程（新功能縮寫）
1. 心夜提交任務 → OMB軍師
2. OMB軍師分派；重大範圍【心夜確認】
3. （可選）會議：每次會議必須參與成員＝OMB軍師＋計劃書軍師＋開發文檔官；結束後文檔官可對齊開發主管安排，重大範圍仍先請心夜確認
4. 計劃書軍師列未確認／承諾【心夜拍板後】起草新版計劃書
5. 軟件設計師給最小範圍與不做【心夜拍板】
6. 開發文檔官出 DEV（未開發狀態）【自動；大改可要心夜知情】
7. 開發主管拆前端／後端任務【自動；後端開工要心夜確認】
8. 前端／後端啟動雲端代理改碼→PR【自動】
9. 對照 DEV 驗收【自動】→ 【心夜確認】合併 main
10. Vercel 自動部署驗證【自動】
11. DEV 狀態改已完成＋OMB軍師交付包【自動／通報】→ 【心夜確認】結案

## 13. 後續可微調（未寫死）

- DEV／計劃書推送是否一律先請心夜確認（現況慣慮是大改先確認）。
- 群組是否固定為範圍議論場，其餘進度只走 OMB軍師彙整。
- Vercel 第一次連接與 Root Directory＝`web` 的驗收步驟是否要單獨成一頁檢查清單。
